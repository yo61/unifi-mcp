## Decision: Move to pnpm 12, add Node 26 to CI, and split the lockfile for osv-scanner

Pin `packageManager` to `pnpm@12.3.4`, add `"26"` to the CI node matrix, and
work around osv-scanner's inability to read the two-document lockfile that
pnpm 12 writes.

## Context

The pnpm pin had drifted to 11.5.3 (2026-06-10) because nothing updates
`packageManager` — Dependabot's npm ecosystem covers `dependencies` and
`devDependencies` only. pnpm 12.3.4 is current, requires `node >=18` (11.5.3
required `>=22.13`), and its one breaking change that could touch us — git
dependencies on known hosts now resolving through canonical HTTPS — is moot
here, since every dependency comes from the registry.

pnpm 12 records the package manager in the lockfile: whenever `packageManager`
is set, `pnpm-lock.yaml` becomes two YAML documents, a `packageManagerDependencies`
record listing all eight `@pnpm/exe.*` platform builds, then the dependency
graph as before. Two things in the pipeline read that file and disagree about
it:

- `check-yaml` rejects multi-document YAML unless told otherwise.
- osv-scanner 2.5.1 (the version pinned in `security.yaml`, and the newest
  release as of today) parses only the first document. Pointed at the new
  lockfile it reports `found 9 packages` and exits 0 — the whole dependency
  graph goes unscanned and the job still passes. Measured: 273 packages before
  the format change, 9 after.

syft/grype are unaffected — the SBOM job still sees 283 components.

## Alternatives considered

- Stay on pnpm 11.26.0 — keeps the single-document lockfile and needs no CI
  change, but declines the upgrade.
- Suppress the record by configuration — there is none. `managePackageManagerVersions`
  in `pnpm-workspace.yaml` is rejected outright by pnpm 12's new strict settings
  check, and both `.npmrc` `manage-package-manager-versions=false` and
  `--config.manage-package-manager-versions=false` still emit the document.
- Drop `packageManager` from package.json — this does produce a single-document
  lockfile, but `pnpm/action-setup` reads that field to choose CI's pnpm, so it
  is what keeps local and CI on the same version.
- Feed osv-scanner the dependency document only — chosen.

## Reasoning

A scanner that fails open is worse than one that fails loudly, so the reduce
step guards itself — but on coverage, not on shape. The packageManager document
carries a `packages:` key of its own, so a shape check would still pass if a
future pnpm emitted the documents in the other order; the step counts
`resolution: {integrity:` lines instead and fails below 200. Verified against
all three shapes: the current lockfile yields 273, a single-document (pnpm 11)
lockfile yields 0, and a reordered pair yields 9.

The reduction happens in place, overwriting the checkout's copy. Writing it to
a side path would put a nonexistent, gitignored filename into every SARIF result
location, which breaks code-scanning alert anchoring and — because alert
identity includes location — closes and recreates every open osv-scanner alert.
The CI checkout is disposable and no later step in that job reads the lockfile.

Node 26 joins 22 and 24 in the matrix. `engines` stays at `>=22.0.0`; the
release job stays on 24, so publishing continues to happen on an LTS.

## Trade-offs accepted

The osv job no longer scans pnpm itself or its eight `@pnpm/exe.*` platform
builds, which are real executed code fetched on every install. They stay covered
by the sbom-scan job, where syft reads the whole lockfile (283 components) and
grype scans it, so an advisory against pnpm 12.x surfaces there rather than
under the `osv-scanner` category.

The reduce step is scaffolding around an upstream gap and has to be removed when
osv-scanner learns to read multi-document lockfiles. Dependabot's handling of a
pnpm-12 lockfile is unverified — the next grouped npm PR is the test, and if it
cannot regenerate the file the pin has to go back to 11.x.
